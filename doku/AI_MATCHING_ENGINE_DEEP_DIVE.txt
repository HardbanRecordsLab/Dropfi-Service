2. **Vector Database** (pgvector in PostgreSQL)

   - Ranks all matches

2. SEMANTIC UNDERSTANDING (Claude's Power)
═══════════════════════════════════════════════════════════════════════════════

Why Claude API, not rules?

Old Way (Rules-based):
───────────────────────
if skill == "photography" and location == "warsaw":
    # Match
else:
    # No match

Problem: Misses nuance!
- "Product photography" vs "Wedding photography" (totally different!)
- "Web design" vs "UI design" vs "Graphic design" (overlaps but different)
- Typos, synonyms, abbreviations break it

New Way (Claude + Semantic):
───────────────────────────
Claude reads the INTENT:
- "Potrzebuję zdjęć produktów e-commerce" 
  → Claude: "OK, e-commerce product photography, not fashion, not wedding"
  
- "Szukamy web designera" 
  → Claude: "Web design = UI + interaction, not print design"

- "FotO productów 100 sztuk"
  → Claude: "OK, product photography, typo detected, 100 items"

This is why Claude >>> rules-based systems!

Claude's Job Analysis Prompt:
─────────────────────────────

from anthropic import Anthropic

client = Anthropic()

JOB_ANALYSIS_PROMPT = """
You are an expert job category classifier. Analyze this job posting and extract:

1. Category: (Photography, Coding, Design, Writing, Marketing, Other)
2. Subcategory: (specific type)
3. Required Skills: (list of 3-5 skills)
4. Urgency: (critical/high/medium/low - based on deadline)
5. Required Experience: (junior/mid/senior)
6. Approximate Fair Price (PLN): (estimate)
7. Key Requirements: (1-2 sentence summary)

Job Title: {title}
Description: {description}
Budget: {budget} PLN
Deadline: {deadline}
Location: {location}

Respond ONLY with valid JSON, no markdown:
{{
  "category": "...",
  "subcategory": "...",
  "skills": ["skill1", "skill2", ...],
  "urgency": "high",
  "experience_level": "mid",
  "fair_price": 3500,
  "key_requirements": "..."
}}
"""

def analyze_job(job):
    response = client.messages.create(
        model="claude-3-5-sonnet-20241022",
        max_tokens=300,
        messages=[{
            "role": "user",
            "content": JOB_ANALYSIS_PROMPT.format(
                title=job.title,
                description=job.description,
                budget=job.budget,
                deadline=job.deadline,
                location=job.location
            )
        }]
    )
    return json.loads(response.content[0].text)

3. VECTOR EMBEDDINGS & pgvector
═══════════════════════════════════════════════════════════════════════════════

What's a Vector Embedding?
──────────────────────────

It's a way to represent MEANING as numbers.

Example (simplified to 3 dimensions):
┌─────────────────────────────────────────────────────────┐
│ Sentence: "Professional product photographer"          │
│                                                          │
│ Converts to vector:                                     │
│ [0.234, -0.891, 0.456, 0.123, ..., 0.789] (1536 dims) │
│                                                          │
│ Key insight: Similar meanings = similar vectors!        │
│                                                          │
│ "Product photographer" ≈ [0.234, -0.891, 0.456...]    │
│ "Photography for products" ≈ [0.235, -0.892, 0.455...] │
│                               ^ Same direction!        │
└─────────────────────────────────────────────────────────┘

Cosine Similarity:
──────────────────

Measures how "similar" two vectors are (0 to 1):

cosine_similarity(v1, v2) = (v1 · v2) / (||v1|| * ||v2||)

Result:
  1.0 = identical meaning
  0.5 = somewhat similar
  0.0 = completely different

Example:
  "Product photography" vs "Product photography" = 0.99 (almost identical!)
  "Product photography" vs "Wedding photography" = 0.65 (related but different)
  "Product photography" vs "Car mechanic" = 0.05 (totally different)

How We Use It in DROPIFY:
─────────────────────────

1. Job comes in → Convert to embedding (1536 dimensions)
   "100 product zdjęć, e-commerce, Warsaw, 5 dni"
   → embedding_job = [0.234, -0.891, ..., 0.789]

2. Search all freelancer profiles → Calculate similarity
   freelancer1: "Product & fashion photographer" 
     → similarity = 0.88 (MATCH!)
   freelancer2: "Wedding photographer"
     → similarity = 0.65 (weak match)
   freelancer3: "UI Designer"
     → similarity = 0.05 (no match)

3. Rank by similarity → Get top 10

4. Further filter & score → Get top 3

pgvector Setup in PostgreSQL:
────────────────────────────

-- Create extension
CREATE EXTENSION IF NOT EXISTS vector;

-- Add embedding columns
ALTER TABLE jobs ADD COLUMN embedding vector(1536);
ALTER TABLE users ADD COLUMN profile_embedding vector(1536);

-- Create index for fast similarity search
CREATE INDEX ON jobs USING ivfflat (embedding vector_cosine_ops);

-- Query: Find freelancers similar to a job
SELECT user_id, 
       1 - (embedding <=> $1) AS similarity  -- cosine distance
FROM users
WHERE role = 'freelancer'
ORDER BY similarity DESC
LIMIT 10;

4. SCORING FORMULA BREAKDOWN
═══════════════════════════════════════════════════════════════════════════════

Final Score = weighted combination of 4 factors:

SCORE = (Semantic * 0.40) + (Rating * 0.25) + (Price_Fit * 0.20) + (Availability * 0.15)

Factor 1: SEMANTIC SIMILARITY (Weight: 40%)
──────────────────────────────────────────

Why highest weight?
  → If skills don't match, don't hire them (no matter how cheap)
  → Vector similarity tells us how good the match is

Calculation:
  semantic = cosine_similarity(job_vector, freelancer_vector)
  → Range: 0.0 to 1.0
  
Example:
  Job: "Product photographer, Warsaw"
  Freelancer: "Professional product photographer, Warsaw"
  semantic = 0.95 ✓ EXCELLENT

Factor 2: RATING (Weight: 25%)
─────────────────────────────

Why?
  → Good freelancers = higher rating
  → Ensures quality

Calculation:
  rating = user.average_rating / 5.0
  → If user has 4.5★ rating → rating = 0.90
  → If user has 2.0★ rating → rating = 0.40
  → If user is new (no rating) → rating = 0.70 (neutral)

Example:
  Freelancer A: 4.8★ → rating = 0.96
  Freelancer B: 3.5★ → rating = 0.70
  Freelancer C: New → rating = 0.70

Factor 3: PRICE FIT (Weight: 20%)
────────────────────────────────

Why?
  → Budget constraints matter
  → Too expensive = client won't hire
  → Too cheap = freelancer won't accept or low quality

Calculation:
  fair_price = job_analysis['fair_price']
  
  if job.budget >= fair_price * 0.8:
      price_fit = 1.0  # Great! Budget enough for quality work
  elif job.budget >= fair_price * 0.5:
      price_fit = 0.5  # Negotiable, might work
  else:
      price_fit = 0.2  # Too cheap, low match probability

Example:
  Fair price: 3500 PLN
  Job budget: 3800 PLN (3800 >= 3500*0.8) → price_fit = 1.0 ✓
  Job budget: 2000 PLN (2000 >= 3500*0.5) → price_fit = 0.5
  Job budget: 1000 PLN (1000 < 3500*0.5) → price_fit = 0.2

Factor 4: AVAILABILITY (Weight: 15%)
───────────────────────────────────

Why?
  → Urgent jobs need fast turnaround
  → If someone is available sooner = higher match

Calculation:
  days_left = (job.deadline - today()).days
  
  if days_left >= 7:
      availability = 1.0  # Plenty of time
  elif days_left >= 3:
      availability = 0.7  # Tight, but doable
  else:
      availability = 0.3  # Very urgent, risky

Example:
  Job deadline: June 25, today: June 20 (5 days left)
  → availability = 0.7

Complete Scoring Example:
────────────────────────

Job: "100 product photos, Warsaw, 3500 PLN, deadline June 25"
Fair price: 3500 PLN

Freelancer A:
  - Semantic: 0.92 (product photographer)
  - Rating: 4.8★ = 0.96
  - Price fit: 3500 >= 3500*0.8 = 1.0
  - Availability: 5 days = 0.7
  
  SCORE = (0.92 * 0.40) + (0.96 * 0.25) + (1.0 * 0.20) + (0.7 * 0.15)
        = 0.368 + 0.240 + 0.200 + 0.105
        = 0.913 ← EXCELLENT MATCH!

Freelancer B:
  - Semantic: 0.78 (photographer but not specialized)
  - Rating: 4.0★ = 0.80
  - Price fit: 3200 >= 3500*0.8 = 1.0
  - Availability: 5 days = 0.7
  
  SCORE = (0.78 * 0.40) + (0.80 * 0.25) + (1.0 * 0.20) + (0.7 * 0.15)
        = 0.312 + 0.200 + 0.200 + 0.105
        = 0.817 ← GOOD MATCH

Freelancer C:
  - Semantic: 0.45 (fashion photographer, not product)
  - Rating: 4.2★ = 0.84
  - Price fit: 2000 < 3500*0.5 = 0.2
  - Availability: 2 days = 0.3
  
  SCORE = (0.45 * 0.40) + (0.84 * 0.25) + (0.2 * 0.20) + (0.3 * 0.15)
        = 0.180 + 0.210 + 0.040 + 0.045
        = 0.475 ← WEAK MATCH

Ranking: Freelancer A (0.913) > Freelancer B (0.817) > Freelancer C (0.475)

6. OPTIMIZATION STRATEGIES
═══════════════════════════════════════════════════════════════════════════════

Challenge 1: Claude API Cost
────────────────────────────
Problem: Each job analysis costs ~0.05 PLN (over time adds up)

Solutions:
1. Cache job analysis results
   - If similar job exists → reuse analysis
   - Store job_analysis in DB

2. Batch analysis
   - Queue jobs, analyze in batch
   - Reduces API calls

3. Smart filtering
   - Rule-based pre-filter (budget, location)
   - Only analyze promising jobs

Example:
def analyze_job(job):
    # Check cache first
    cached = redis.get(f"job_analysis:{job.category}:{job.skills}")
    if cached:
        return json.loads(cached)
    
    # Not cached, call Claude
    analysis = claude_api_call(job)
    
    # Cache for 7 days
    redis.setex(f"job_analysis:...", 7*24*3600, json.dumps(analysis))
    return analysis

Challenge 2: Embedding Costs
────────────────────────────
Problem: OpenAI embedding = 50 PLN/month

Solutions:
1. Local embedding model
   from sentence_transformers import SentenceTransformer
   
   model = SentenceTransformer('all-MiniLM-L6-v2')
   embedding = model.encode("Product photography")  # free!
   
   Tradeoff: Slightly lower quality but 100% free

2. Cache + reuse
   - Same skills → same embedding
   - Freelancer profile updated → recalculate only freelancer

Challenge 3: pgvector Performance
─────────────────────────────────
Problem: Vector search slow with 10k+ vectors

Solutions:
1. Index creation (already done):
   CREATE INDEX ON jobs USING ivfflat (embedding vector_cosine_ops);

2. Approximate search instead of exact
   - IVFFlat (approximate) vs exact
   - Trade 1% accuracy for 10x speed

3. Pre-filter before vector search
   - Filter by category, location, price FIRST
   - Then vector search on 100 candidates (not 10k)

Example optimized query:
SELECT user_id, 
       1 - (embedding <=> $1) AS similarity
FROM users
WHERE role = 'freelancer'
AND location ~ 'Warsaw'  -- filters first!
AND skills @> $2  -- JSON filter
AND price_rate BETWEEN $3 AND $4  -- price filter
ORDER BY similarity DESC
LIMIT 20;

Implementation:
def get_fair_price(job_analysis):
    # Query similar jobs from last 3 months
    similar_jobs = db.query(Job).filter(
        Job.category == job_analysis['category'],
        Job.created_at > now() - timedelta(days=90)
    ).all()
    
    # Calculate median price
    prices = [j.budget for j in similar_jobs if j.status == 'completed']
    fair_price = median(prices)
    return fair_price
